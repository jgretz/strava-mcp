## Findings

### Architecture — A

- Layered separation is clean: `types/utils/config` → `auth` → `api` → `tools` → `index`. Dependencies flow one direction.
- One tool per file, data-driven registration via array iteration — matches the Coros reference pattern exactly.
- API domain modules are thin wrappers over the generic client — high cohesion, low coupling.
- `stravaGetText` now has 401 retry parity with `stravaRequest`. The inner `fetchText` closure is slightly awkward but functional; acceptable tradeoff for not over-abstracting.

### Code Quality — A

- `formatDuration`/`formatDistance` extracted to shared `src/tools/format.ts` — no duplication across tool files.
- Stream stats use `reduce` instead of spread — safe for large arrays.
- Numeric param checks use `!== undefined` — handles `page=0` correctly.
- `as const` on config objects, proper nullability on all Strava types.
- `src/auth/store.ts:1` — Uses `node:fs` sync functions where `Bun.file` is idiomatic per project CLAUDE.md. Low priority since it works and the file ops are small.
- `src/api/segments.ts:38` — `opts.perPage` still uses truthiness check (`if (opts.perPage)`) rather than `!== undefined`. Same for `startDate`/`endDate` — strings are fine with truthiness since empty string is falsy and unlikely, but `perPage` as a number could theoretically be 0.

### Design Patterns — A

- `Result<T, E>` used consistently across all layers — no throws anywhere in the codebase.
- `defineTool()` factory provides type safety without boilerplate; `McpTool` type enables the data-driven registration loop.
- Tool handlers follow a consistent pattern: call API → early return on error → format text. Pure data transformation.
- API import aliasing (`as fetch*`) in tool files cleanly resolves the naming collision without sacrificing readability.

### Testing — B+

- **auth.test.ts**: Tests the full token cascade — cached valid, cached expired, refresh with mocked fetch, 60s expiry boundary. Properly isolates from env vars AND stored token file via backup/restore.
- **store.test.ts**: Clean env var isolation with afterEach restore.
- **client.test.ts**: Tests both `stravaGet` and `stravaGetText` — auth errors, Bearer token injection, HTTP failures, success parsing. Consistent `afterEach` cleanup.
- **format.test.ts**: Edge cases (zero, exact hour, large distances).
- `tests/auth/auth.test.ts:22-34` — The token file backup/restore pattern is necessary but fragile if tests crash mid-run (token file would be deleted). Acceptable for a project of this size.
- No tests for 401 retry behavior in client — the auto-retry on token expiry is an important integration path worth covering.
- `src/tools/routes/list-athlete-routes.ts` calls `getToken()` directly in the handler (to get `athleteId`), bypassing the pattern where the API client handles auth. Not a bug, but a minor coupling concern.

### Naming & Docs — A-

- Export names are now consistent — no `Tool` suffix anywhere.
- Types centralized in `src/types.ts` including `ExploreSegmentsResponse`.
- `isExpired` comment explaining the 60s buffer is a good "why" comment.
- `src/config.ts:4` — `ACTIVITY_TYPE_LABELS` is typed `Record<string, string>` but also uses `as const`. The `as const` is effectively a no-op since the explicit type widens it. Minor inconsistency — either drop `as const` or use a narrower type.

## Summary

The codebase is well-structured, follows established patterns consistently, and addresses all issues from the previous review. The main areas for future improvement are:

1. Minor: `perPage` truthiness check in `segments.ts:38`
2. Minor: `as const` on `ACTIVITY_TYPE_LABELS` is redundant with the `Record<string, string>` type
3. Nice-to-have: 401 retry integration test in client.test.ts
4. Nice-to-have: Migrate `node:fs` to `Bun.file` in store.ts
